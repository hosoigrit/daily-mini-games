# テスト用fixture・手順補足 v0.6
設計資料のみ。以下はテスト実装の入力条件。実際の音楽・ゲームのソース・実行結果ではない。全ケースで独立初期化、固定SHA/環境/実測/期待比較を記録。各TCの個別条件が優先。

## 1. 単体・統合の共通fixture
- TIME: 固定時計、BPM100、PPQ480、1tick=1250μs。補正0、単一有効session、正常lease、時刻変換アンカーを用意。曲時刻を進める場合は入力を受信順にenqueueし、Wの境界の前/同値/後を独立検査。例外試験のみ不正値注入。実ブラウザが作れないμsは論理レイヤーへ直接注入し、正式譜面のtick検査と区別する。
- NOTE: 通常レーン1 target1000ms、入力主体LEFT、押下50ms後UP。候補競合試験の100ms間隔などは判定器専用の合成イベント、正式譜面の構造検証には投入しない。CHORDはレーン1/3同一時刻、HOLDは1の1000→2000ms。別の明示条件を持つTCはそちらを使う。
- SCORE: N>0。ライフ初期200内部units、ケースで指定された中間値はテスト用純粋reducerまたは到達可能な確定履歴を使う。成功グループと空打ちの論理順序を記録。N=200 P180/G17/GOOD3は964000、空打ち3は961000。ロング開始失敗は終了時刻まで追加ダメージなし。FAILEDは未確定判定を未プレイへ。
- SAVE: 初期epoch E0、revision0、Track01のみ解放、設定既定。既存レコードを置く場合は解放・品質・称号・判定内訳と整合するfixtureを生成。新規sessionはIDが重複しない。模擬setItem/読戻し失敗は別々に注入。ブラウザ競合は同一originの2ページで行い、ロックは実APIで検査。
- CAL: BPM100、16拍のbeatを600ms間隔で生成、拍1〜4はウォームアップ。評価拍ごとの誤差をTCの値で入力。各押下間で解放を挟む。入力0から±300msを走査、既使用拍を再割当しない。最後の拍+300ms、配送待ち境界を越えて提案する。
- CONTENT: 正式楽曲は各Stageの完成済み対象だけ。Stage Aは試験楽曲/譜面、Stage BはTrack01の3譜面、Stage C/Dは全5曲15譜面。未制作・対象外を全件PASSと記録しない。

## 3. ランク・解放・称号用fixture
rank境界: 0,699999,700000,700001,799999,800000,800001,899999,900000,900001,949999,950000,950001,979999,980000,980001,1000000。CLEAR/FAILEDはrankと独立。FAILEDはlife=0、CLEARは全判定確定かつlife>0。得点の手入力はrank単体テストのみ、保存統合は整合する判定内訳から生成。
称号: ACH-01は0→1 CLEAR。02はMISS・空打ち・未プレイなしのCLEAR（GOOD可）、03は全P/空打ち0。04は各曲1件CLEAR（4曲では未達）、05は14→15譜面CLEAR、06は4→5 HARD CLEAR、07は14→15譜面S以上（最後Aは未達）、08は14→15 AP（最後GREATありは未達）。初回APは01/02/03を同一保存で更新。再達成で重複禁止。

## 4. 実機・E2Eと評価証跡
- DEV: 実機5環境、タッチは3端末、物理キーはPC2環境。各DEV-T01〜13を本仕様§10に従い実行。各試行のブラウザ版、OS、画面寸法、音声出力先、操作・合否・証跡を記録。対象外をN/A、未実施をNOT RUN。性能の実行はPF基準。独立レビューの合格には固定SHAと評価者が必要。
- QUALITY: MQ/CQ/VQ各項目の0〜5と採点理由、聴取/プレイ範囲、評価者、対象SHAを保存。最低点方式、各下限と平均、重大VIS/権利を別判定。未評価の音楽的魅力は波形検査で代替しない。Stage Bは差別化を除外した換算。TC-D4-074〜078/TC-D5-018/025は評価シートと証跡を参照。
- RELEASE: source/production比較は同一入力シナリオ、公開予定ファイルはSHA256で全数照合、公開後は配信物と別記録。既存ゲーム回帰対象は#0001〜0010の承認済み必須項目（現行リポジトリで特定）。

## 5. 完成していないfixture
本書の共通fixture・具体化した境界値は設計の入力条件であり、全310 IDに対する個別実行ファイルではない。各契約の正常/異常の厳密なfixture、各画面操作・全コマンド組合せの具体的な手順、生成された正式コンテンツ、各実機操作ログは未作成。承認時に設計の引継ぎ対象として明確化し、凍結前に仕様の全件意味レビューを行う。

## v0.7 補足 fixture
- CHART: BPM100/PPQ480、tick480=600ms。単体のノーツ展開・親指局所制約の最小fixtureは正式5曲15譜面の密度・全4種類/全4レーン・曲長などの全体制約を対象外とする。正式検証器の統合負例は正常正式チャートの対象箇所だけを変更し、違反コードが含まれることを確認。複数違反時の最初のエラーコードは固定しない。
- SESSION: 固定clock、現session S1、正常lease、保存済み条件、対象画面、音源準備完了。各TCが指定する例外だけを変える。再開世代は新ID。操作直積表の条件付き行は追加guardの正常/個別違反を作成する。
- UI: 9画面と子画面、画面遷移表と物理DOM要素。StrictModeのmount/cleanupを記録、実機専用条件は物理端末で検証。
- CONTRACT: IF-01〜20の型・事前条件・エラーの正例/負例を対象契約別に注入。ゲーム実装後の契約実行結果と設計型チェックは別。
- AUDIO: 全5曲定義の音源生成・イベント・バッファーを記録。48kHz stereoで各曲frame数を照合。SFXの理論合成ピークと実波形を分けて検査。
- SCOREの低ランクCLEAR等: テスト専用reducerまたは整合する実履歴を作り、保存テストでは不可能な判定内訳を入力しない。特定の正式譜面で要求fixtureを作成不能ならBLOCKEDとして理由を記録し、勝手に期待値を変更しない。

# Phase 4 引渡し・承認ゲート
1. v0.8の21原本、v1.0正本、承認記録、計画、検査ログをローカル凍結候補として固定。全SHA256を照合。
2. 登録許可前に対象repo、main SHA、候補ブランチ、全対象パスを再読取。競合や既存成果物があればHOLD。登録許可はこのパッケージの指定ファイルだけ。mainから新規docs/game-0011-handoffを作成し handoffs/game-0011/v1.0/ にテキストを原文登録、読み戻しSHA256照合、mainが当該操作で変更されていないことを確認。外部同時更新は区別。PR/merge/公開/実装禁止。
3. 登録結果のコミットSHA・ファイル数・ハッシュ・差分を報告。Phase 4完了判定は登録と照合後。次にStage A-1だけの開始を別承認。承認された固定コミットから設計を読み込む。作業ブランチの起点・取得方法は開始承認時に固定。既存作品や共通資産変更は別承認。

Stage A-1: 依存候補確定・型/契約・開発基盤、POC-13/14/16/18の基盤適用範囲。実証が必要なものはA-2へ割当、実行されなければNOT RUN。Stage A-2: 試験曲/譜面、POC-01〜08,10,15,17および基盤統合。Stage A-3: POC-09/11/12、指定5環境、全適用POC18判定。各段階の完了・次段階開始にユーザー承認。Stage B: Happy Assembly/3譜面/1工場/6品質、REF-01〜10+暫定VQ、暫定MQ/CQ/VQ、人間評価。Stage C: 残4曲/12譜面/4工場と正式採点。Stage D: 全機能、独立レビュー、是正、実機、既存10作品、QG-01〜11（QG-10-postのみ公開後）。
5. FIN-09/10/11の独立意味確認は実装開始時から各担当が対応要件の全条件・TC・fixtureを照合し、欠落・矛盾は該当実装前にHOLD。独立レビュー担当は実装後に再確認。基準変更はユーザー承認。CRITICAL/HIGH未解決禁止、MEDIUM個別承認、LOW記録。原則最大5是正ループ。
6. 実装側reportsにSHA、環境、実行者、エージェント独立性、実行ログ、未実施/失敗、評価、修正履歴を保管。大容量証跡は登録前に承認。エミュレーションを実機としない。音声を聞けないエージェントは試聴NOT RUN。13役割は実際の起動数を意味しない。GitHub push、PR、merge、公開は各別承認。

## TP-01 目的・原則

1. Must要件FR-01〜20、FR-22、FR-24、FR-26および非機能NFR-01〜11の適合を検証する。
2. Should要件FR-21、FR-23、FR-25は実装採否をレビューで記録し、採用時には対応テストを実施する。Shouldの未採用はMust不合格と混同しない。
3. 要件の受入条件AT-01〜20へテストケースを紐づける。
4. ロジックの機械的検証と、視認性・触り心地・難易度の人間による試遊を分離する。
5. 実行結果は証拠のあるPASS、FAIL、BLOCKED、NOT_RUN、N/Aで記録。実施していない確認を推測PASSにしない。

### 判定語

| 状態 | 意味 |
|---|---|
| PASS | 手順と期待結果を照合し、必要な証跡を確保した |
| FAIL | 期待結果との差異を確認した |
| BLOCKED | 前提環境・権限・対象成果物がなく実施不可 |
| NOT_RUN | まだ実施していない |
| N/A | 非採用のShouldなど、適用対象ではない。理由を残す |

### 生成制約の大量試験（AT-19）

各難易度**100件以上**の生成候補を、再現可能な乱数系列で検証する。

- accepted候補：静止機体への計算上の初期接触時間が1.2秒以上。
- rejected候補：1.2秒未満で採用されない。
- 上限体数：常にEASY 3、NORMAL 4、HARD 5以下。
- 候補10回連続棄却：必ず当該生成処理を終了。
- 同じseed＋同じ入力・ステップ列：出現辺・位置・速度が再現する。
- 目的は**単一生成の制約検証**。複数隕石の全局面で回避可能と断定しない。

| 記録項目 | 観察の例 |
|---|---|
| ライフ結果 | クリア3/2/1、失敗、失敗した秒数 |

**バランス判定の考え方：**

- 「必ず避けられる」は合格条件にしない。
- 生成時間下限の違反・操作不能・視認できない衝突は不具合候補。
- 連続的に同じ位置で理不尽な被弾が起こる場合はシード、発生時刻、位置、スクリーンショットを残し、再現を試みる。
- 初回3回だけで公正性を保証しない。疑義があれば試遊を追加し、調整前後を記録する。
- 必要なチューニングは実装承認後に実施するもので、この計画文書作成時点では行わない。

## TP-07 記録様式・不具合票

**テスト結果レコード：**

| 欄 | 記録 |
|---|---|
| Test ID | UT-001等 |
| 要件ID | FR-xx、NFR-xx、AT-xx |
| 環境 | OS、ブラウザ版、機種、画面方向 |
| 実施日時 | 日本時間 |
| 手順・入力 | seed、ステップ、キー、Pointer操作など |
| 期待結果／実際結果 | 数値や画面表示 |
| 判定 | PASS/FAIL/BLOCKED/NOT_RUN/N/A |
| 証跡 | 実行ログ、画面画像、再現条件 |
| 担当・再確認 | テスト実施者、修正後の再試験日 |

**不具合票：** ID / 重要度（Critical, High, Medium, Low） / 再現手順 / 期待・実際 / 環境 / 原因（未確定可） / 修正方針 / 再テスト結果 / 未解決理由。

重要度は次の順：Crash・進行不能・残ライフ矛盾＝Critical、操作固着・30秒判定不正＝High、画面崩れ等＝Medium、外観の軽微差＝Low（案）。

## TP-08 合否ゲートと独立レビュー

1. 基本設計の正式承認前は**本計画自体も未承認**とし、実装・テストを開始しない。
